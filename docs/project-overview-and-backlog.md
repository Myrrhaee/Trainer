# AI Strength Coach: карта проекта и backlog

Дата аудита: 2026-06-22

## 1. Короткое описание проекта

AI Strength Coach - премиальный web-продукт для двух связанных аудиторий:

- клиент тренируется, ведет дневник, смотрит прогресс, пользуется библиотекой упражнений и получает работу от тренера;
- тренер ведет клиентов, видит очередь внимания, назначает тренировки, разбирает выполненные сессии, управляет шаблонами, программами и витриной.

Текущая основная активная цель: довести тренерский кабинет до состояния понятного рабочего центра, где тренер сразу видит, кто требует внимания и какое действие нужно сделать дальше.

Главная продуктовая ось:

```text
Client -> Attention Item -> Action -> Next Client
```

Это значит, что приоритет сейчас не в расширении количества разделов, а в закрытии рабочего цикла тренера:

```text
увидел клиента с задачей -> открыл контекст -> назначил/разобрал/написал -> задача исчезла из очереди
```

## 2. Текущее состояние

### Сильные стороны

- Есть рабочая premium-dark визуальная система: черный/zinc фон, lime-акцент, крупные панели, плотная тренерская подача.
- Клиентский demo-кабинет уже задает хороший UX-бар: тренировки, библиотека, активность, прогресс, настройки.
- Новый `/trainer/*` уже содержит почти полный набор разделов: dashboard, clients, client detail, builder, programs, calendar, library, messages, reports, automation, insights, sales, settings.
- `/trainer/dashboard` уже не выглядит как обычный KPI-dashboard: это скорее trainer OS с состоянием команды, action stories, activity feed, quick assign и review drawer.
- `/trainer/clients` уже близок к рабочему roster: фильтры, поиск, статусы, действия, demo/real data bridge.
- `/trainer/builder` имеет реальную функциональную глубину: библиотека упражнений, упражнения в тренировке, per-set mode, шаблоны, draft, сохранение.
- Lint проходит: `npm run lint` успешно.

### Главные риски

- В проекте одновременно живут новый `/trainer/*` и старый `/dashboard/*`. Это размывает продукт, роутинг и ментальную модель.
- Demo-login тренера все еще ведет на `/dashboard`, хотя активная зона - `/trainer/dashboard`.
- Attention Item пока в основном UI/demo-сущность, а не каноническая persisted-модель.
- Quick Assign находится в основном на главной тренера, но должен стать глобальным действием из roster, карточки клиента, review и attention.
- Навигация неоднородна: sidebar показывает 4 основных раздела, command palette знает сильно больше разделов.
- Клиентские страницы частично раздвоены: `/client/me` живой, а `/client/workouts`, `/client/activity`, `/client/progress` в demo mode показывают большие demo-экраны, иначе редиректят.
- Визуальная проверка через browser-коннектор не выполнена из-за внутренней ошибки окружения; HTTP-проверка основных маршрутов прошла.

## 3. Главная страница

### Назначение

Главная страница `/` должна объяснить продукт и развести пользователя в нужный сценарий:

- клиент хочет начать тренироваться;
- тренер хочет создать кабинет;
- авторизованный пользователь хочет вернуться в свой кабинет.

### Что уже есть

- Landing находится в `components/landing/landing-page.tsx`.
- Есть переключатель "Для себя" / "Для тренеров".
- Есть CTA на `/login?role=client` и `/login?role=trainer`.
- Если пользователь уже авторизован, landing пытается определить роль и показать кнопку "В кабинет".

### Что нужно доработать

1. Привести trainer CTA и auth redirects к новому `/trainer/dashboard`.
2. Уточнить позиционирование для тренера: сейчас текст ближе к "CRM для тренеров", а продуктовая модель уже богаче - "операционный центр внимания и назначения".
3. Добавить более честный первый viewport продукта: сейчас есть стилизованные mock-телефоны, но для premium fitness OS лучше показывать реальный фрагмент client/trainer UI или сильный визуальный asset.
4. Свести landing к ясному обещанию: клиенту - "что делать сегодня", тренеру - "кто требует внимания сейчас".

## 4. Личный кабинет клиента

### Назначение

Кабинет клиента должен отвечать на вопрос:

```text
Что мне делать сегодня и как мой прогресс меняется?
```

### Основные активные зоны

- `/client/me` - главная клиента.
- `/client/library` - библиотека упражнений.
- `/client/settings` - профиль и настройки.
- `/check-in` - чек-ин, вес, самочувствие.
- `/history` - история.
- `/programs` - программы клиента.
- `/workout/free` - свободная тренировка.
- `/client/[id]` и `/client/[id]/program/[programId]` - выполнение/просмотр клиентской тренировки и программы.

### Что уже хорошо

- Demo client cabinet очень сильный как эталон качества.
- Есть сценарии клиента: с тренером, без тренера, без программы, с активной программой.
- Библиотека упражнений визуальная и полезная.
- Есть механики workout logging, прогресса, активности и настроек.
- Клиентский визуальный язык уже ближе к нужному premium fitness feel.

### Что нужно доработать

1. Определить canonical routes: оставить `/client/me` как главную и решить судьбу `/client/dashboard`, `/today`, `/client/workouts`, `/client/activity`, `/client/progress`.
2. Синхронизировать demo-экраны и реальные экраны, чтобы пользователь не попадал в разные продукты в зависимости от demo mode.
3. Связать клиентский workout log с тренерским review loop: завершенная тренировка должна создавать понятную задачу тренеру.
4. Убедиться, что тренерская карточка клиента использует те же сущности прогресса, что клиентский кабинет: вес, история, чек-ины, нагрузки, комментарии.

## 5. Личный кабинет тренера

### Назначение

Кабинет тренера должен отвечать на вопрос:

```text
Кому я нужен сейчас и какое действие быстрее всего улучшит ситуацию?
```

### Текущие разделы `/trainer/*`

- `/trainer/dashboard` - главная тренера, состояние команды и action flow.
- `/trainer/attention` - центр внимания.
- `/trainer/clients` - roster клиентов.
- `/trainer/clients/[clientId]` - карточка клиента.
- `/trainer/review/[workoutId]` - разбор тренировки.
- `/trainer/builder` - конструктор тренировки/шаблона.
- `/trainer/programs` - программы.
- `/trainer/calendar` - недельное планирование.
- `/trainer/library` - библиотека упражнений.
- `/trainer/messages` - сообщения.
- `/trainer/reports` - weekly reports.
- `/trainer/automation` - правила follow-up.
- `/trainer/insights` - риски и аналитика.
- `/trainer/sales` - продажи.
- `/trainer/settings` - настройки.

### Что уже хорошо

- Новый TrainerShell уже создает ощущение отдельного trainer OS.
- Главная тренера визуально и концептуально сильнее старого dashboard.
- Есть Quick Assign Drawer и Workout Review Drawer.
- Есть client roster с поиском, фильтрами, attention states и быстрыми действиями.
- Есть клиентская карточка как demo-концепт полного coaching context.
- Builder уже функционально ценный, его не нужно выбрасывать.

### Что нужно доработать

1. Сделать `/trainer/dashboard` единственной главной точкой тренера.
2. Перевести auth/demo redirects с `/dashboard` на `/trainer/dashboard`.
3. Сократить MVP-навигацию до рабочего ядра:
   - Главная
   - Клиенты
   - Шаблоны/Builder
   - Библиотека
   - Настройки
4. Оставить остальные разделы доступными через command palette или второй слой, пока они не стали реальными ежедневными workflow.
5. Сделать Attention Item канонической сущностью: хотя бы сначала как единый typed adapter, затем как таблица.
6. Вынести Quick Assign в общий workflow, доступный из dashboard, clients, client profile, review и attention.
7. Связать review completion с закрытием related attention item.
8. Решить, что важнее в MVP: templates first или programs first. По текущей operating model templates должны быть первичнее программ.

## 6. Backlog по приоритетам

### P0 - сейчас, чтобы убрать продуктовую путаницу

1. Закрепить canonical trainer route.
   - Все входы тренера должны вести на `/trainer/dashboard`.
   - Demo login, signup, client settings redirect и role-based landing button не должны отправлять тренера на legacy `/dashboard`.

2. Принять решение по legacy `/dashboard/*`.
   - Минимум: скрыть из основных переходов.
   - Лучше: сделать redirect на соответствующие `/trainer/*`.
   - Не удалять сразу, пока из legacy не вынесена полезная Supabase-логика.

3. Зафиксировать MVP-навигацию тренера.
   - Sidebar сейчас показывает ядро, command palette - расширенный список.
   - Нужно явно записать: какие разделы ежедневные, какие experimental/secondary.

4. Сформулировать canonical Attention Item contract.
   - `clientId`
   - `reason`
   - `urgency`
   - `source`
   - `primaryAction`
   - `secondaryAction`
   - `status`
   - `createdAt`
   - `resolvedAt`

### P1 - ближайшая разработка тренерского кабинета

1. Global Quick Assign.
   - Вынести drawer/provider.
   - Открывать из клиента, очереди внимания, review, календаря.
   - После назначения закрывать задачу и предлагать следующего клиента.

2. Trainer dashboard как command center.
   - Оставить сильную текущую концепцию, но добавить более явный список next actions.
   - Убрать ощущение, что dashboard, attention, insights и calendar конкурируют за один вопрос "что делать дальше?".

3. Clients roster -> client detail loop.
   - Из каждого клиента должен быть понятный primary action.
   - Карточка клиента сверху должна отвечать: состояние, риск, следующее действие.

4. Review loop.
   - Завершенная клиентом тренировка создает review task.
   - Отправленный review закрывает task.
   - После review можно назначить следующую тренировку без перехода в тяжелый builder.

5. Builder visual/product upgrade.
   - Сохранить функциональное ядро.
   - Сделать его более похожим на премиальный рабочий инструмент из client demo.
   - Поднять templates как основной объект.

### P2 - после стабилизации trainer core

1. Programs как вторичный слой над templates.
   - Программа = упаковка/цикл/витрина.
   - Template = ежедневная операционная единица.

2. Calendar как derived view.
   - Не отдельный центр управления, а недельный срез attention/workout/check-in events.

3. Messages.
   - Решить, это настоящий chat или оболочка над Telegram/follow-up.
   - Не позволять messages конкурировать с Attention Queue.

4. Reports.
   - Делать отчеты из контекста клиента и недельного итога.
   - Не превращать reports в отдельный тяжелый раздел до готовности данных.

5. Sales.
   - Оставить как business layer, но не ставить в центр coaching MVP.
   - Связать с public trainer profile и program products.

### P3 - позже

1. Automation rules -> attention outputs.
   - Автоматизация должна создавать/предлагать Attention Items, а не жить отдельным миром.

2. Insights.
   - Делать только после появления стабильных данных: adherence, workout logs, reviews, check-ins.

3. Полная Supabase-нормализация.
   - `attention_items`
   - `workout_assignments`
   - четкое разделение planned workout / completed workout / review.

4. Визуальный QA по всем breakpoints.
   - Desktop 1440.
   - Tablet.
   - Mobile 390.
   - Проверить sticky headers, drawers, overflow, длинные русские строки.

## 7. Рекомендуемый порядок следующих задач

1. Поправить redirects тренера на `/trainer/dashboard`.
2. Создать короткий route decision doc: что canonical, что legacy, что redirect-only.
3. Упростить trainer navigation для MVP и вынести вторичные разделы в command palette.
4. Описать и внедрить единый `AttentionItem` тип в trainer OS.
5. Вынести Quick Assign из dashboard-local сценария в общий компонент/workflow.
6. Привязать workout review к закрытию attention item.
7. Улучшить `/trainer/clients/[clientId]`: верхний блок "состояние -> риск -> следующее действие".
8. После этого возвращаться к Builder и делать visual/product polish.

## 8. Definition of Done для ближайшего этапа

Ближайший этап можно считать закрытым, когда:

- тренер после входа всегда попадает в новый `/trainer/dashboard`;
- старый `/dashboard/*` больше не выглядит как основная часть продукта;
- на главной тренера есть понятная очередь действий;
- из roster и карточки клиента можно быстро назначить тренировку;
- разбор тренировки закрывает соответствующую задачу;
- клиентский completed workout виден тренеру как review item;
- lint проходит;
- ключевые страницы проверены визуально хотя бы на desktop и mobile.
