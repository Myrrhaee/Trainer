# Trainer OS V1: шесть последних продуктовых ответов

Дата: 2026-06-19

Документ объединяет ответы на последние шесть продуктовых запросов по Trainer OS:

1. Аудит Trainer Dashboard с предположением, что 50% интерфейса нужно убрать.
2. Выбор визуального архетипа продукта.
3. Идеальная главная страница тренера с позиции Head of Product.
4. Аудит Client Profile.
5. Аудит drawers и модалок.
6. Стартап-анализ дифференциации относительно Trainerize, TrueCoach, Everfit и My PT Hub.

Главный контекст:

```text
Продукт: Trainer OS для премиального онлайн-тренера
Аудитория: 10-30 активных клиентов
Главный объект: клиент / спортсмен
Основной цикл: Team -> Client -> Attention / Decision -> Action -> Next Client
```

## 1. Аудит Trainer Dashboard: что оставить, убрать, объединить

### Главный вывод

Текущий Trainer Dashboard все еще рискует ощущаться как смесь:

- CRM;
- SaaS-dashboard;
- team management board;
- визуальная демо-страница.

Для тренера, который открывает страницу на 30 секунд, важны только четыре вопроса:

1. Все ли в порядке с командой?
2. Кто требует моего решения прямо сейчас?
3. Что произошло недавно?
4. Как быстро открыть клиента или выполнить действие?

Если элемент не помогает ответить на эти вопросы, он должен быть удален, объединен или визуально понижен.

### Что остается

| Блок | Решение | Почему |
|---|---|---|
| Team Map | Keep | Это главный отличающийся объект страницы: команда как живой состав, а не таблица клиентов |
| Action Queue | Keep | Это главный рабочий блок: кто заблокирован и что сделать |
| Compact Team Summary | Keep, но сильно сжать | Нужно быстро понять состояние команды, но без KPI-wall |
| Recent Meaningful Activity | Keep, но сократить | Помогает почувствовать жизнь команды, но не должен конкурировать с Action Queue |
| Primary CTA | Keep | Тренеру нужен явный вход в работу: "Обработать клиентов" |

### Что убрать

| Блок | Решение | Почему |
|---|---|---|
| Большие KPI-карточки | Remove | Делают страницу похожей на BI-dashboard |
| Финансовые метрики | Remove | Деньги не должны конкурировать с coaching flow |
| Большие графики | Remove | На главной они создают аналитический шум |
| Calendar-first блоки | Remove from primary area | Главная не должна становиться календарем |
| Повторяющиеся списки клиентов | Remove | Дублируют Team Map и Action Queue |
| Большие декоративные карточки без действия | Remove | Они замедляют восприятие |
| Слишком подробный Secondary Attention | Remove / collapse | Замеры и чек-ины важны, но не должны конкурировать с заблокированной тренировкой |

### Что объединить

| Текущий смысл | Как объединить |
|---|---|
| Header + Summary | В одну компактную строку состояния: "24 спортсмена · 18 по плану · 3 требуют действий" |
| Team Map + Legend | Легенду встроить рядом с картой, а не делать отдельным визуальным блоком |
| Action Queue + Selected Client Preview | При выборе клиента в карте подсвечивать его в очереди или давать компактный preview |
| Activity Feed + Recent Done | Оставить 3-5 последних осмысленных событий |
| Secondary Attention + Soft Issues | Свернуть в одну строку: "Плановые проверки: замеры 4 · чек-ин 2 · вес 3" |

### Что должно стать вторичным

| Элемент | Как понизить |
|---|---|
| Secondary Attention | Сделать компактной строкой или маленьким блоком внизу |
| Activity Feed | Сократить до нескольких событий, без больших карточек |
| Summary metrics | Оставить как composed summary, не как набор отдельных KPI |
| Calendar/planned events | Показывать только если есть важная тренерская задача |

### Рекомендуемая V1-композиция Dashboard

```text
HEADER
Команда Романова
24 спортсмена · 18 по плану · 3 требуют действий
[Обработать 3]

MAIN
Team Map
Визуальная карта всех клиентов как команды

ACTION AREA
Action Queue
Только 3-5 клиентов, у которых заблокирован тренировочный процесс

RECENT
3 последних осмысленных события

SECONDARY
Плановые проверки: замеры 4 · чек-ин 2 · вес 3
```

### Ответ на вопрос "если тренер открыл страницу на 30 секунд"

Помогают:

- карта команды;
- явно выделенные заблокированные клиенты;
- одна главная кнопка обработки;
- короткая последняя активность;
- быстрый переход в клиента.

Не помогают:

- KPI;
- подробные метрики;
- длинные списки;
- финансовые показатели;
- calendar-first сетка;
- декоративная аналитика.

## 2. Лучший визуальный архетип Trainer OS

### Сравнение архетипов

| Архетип | Что полезно | Что опасно |
|---|---|---|
| Linear | Очередь задач, фокус, плотность, ясные статусы | Может стать слишком инженерным и холодным |
| Notion | Спокойствие, ясная структура, ощущение рабочего пространства | Может стать слишком документным и рыхлым |
| Arc Browser | Премиальность, легкость, выразительная оболочка | Риск декоративности вместо операционного фокуса |
| Discord | Чувство клуба и живого сообщества | Слишком чатовый и шумный для coaching workflow |
| Slack | Быстрые каналы и коммуникация | Не подходит как главный coaching OS, слишком messaging-first |
| Formula 1 pit wall | Операционный контроль, сигналы, команда, решения | Риск стать перегруженным мониторингом |
| Wealth management platforms | Премиальная спокойная уверенность, работа с портфелем клиентов | Риск стать слишком финансовым и пассивным |
| Professional sports team software | Команда, атлеты, performance, coaching context | Риск перегрузить спортивной аналитикой |

### Рекомендуемый основной архетип

```text
Private Athlete Management Office
```

Это не один существующий продукт, а комбинация:

- professional sports team software;
- wealth management interface;
- Linear-like operational queue.

Тренер должен чувствовать, что управляет не CRM-базой, а небольшой частной командой спортсменов.

### Визуальный язык

Нужен язык:

- спокойный;
- дорогой;
- темный;
- плотный, но не зажатый;
- с минимальным количеством декоративного свечения;
- с людьми как главным объектом;
- с ясным разделением "все в порядке" и "нужно решение".

Не нужен язык:

- дешевого фитнес-неона;
- CRM-таблиц;
- маркетинговых карточек;
- BI-дашборда;
- игрового интерфейса;
- календарной сетки как главного объекта.

### Layout philosophy

Правильная философия layout:

```text
Team first
Decision second
Activity third
Admin last
```

Страница должна начинаться не с метрик и не с задач, а с ощущения состава команды.

### Interaction model

Лучший interaction model:

```text
See team
Spot blocked athlete
Open quick action drawer
Assign / review / message
Close task
Move to next athlete
```

Тренер не должен уходить в длинные страницы для быстрых действий.

### Основной архетип и вторичные вдохновения

Primary:

```text
Professional sports team command center for a private coaching club
```

Secondary inspiration 1:

```text
Linear
```

Для очередей, статусов, скорости обработки и ощущения "следующее действие всегда понятно".

Secondary inspiration 2:

```text
Wealth management platform
```

Для премиального спокойствия, доверия, работы с ограниченным портфелем важных клиентов.

## 3. Идеальная главная страница тренера

### Главная задача страницы

Главная страница должна отвечать:

1. Как моя команда?
2. Кто требует моего решения?
3. Что произошло недавно?
4. Как быстро действовать?

Это не dashboard в классическом смысле. Это home base тренера.

### Информационная иерархия

```text
1. Состояние команды
2. Клиенты, у которых заблокирован тренировочный процесс
3. Последние осмысленные события
4. Быстрые действия
5. Вторичные soft-issues
```

Важно: заблокированный тренировочный процесс важнее, чем отсутствие замеров или чек-ина.

### Layout

```text
TOP
Название команды + compact status summary + primary action

CENTER
Team Map
Все клиенты видны как спортсмены команды

RIGHT / BELOW
Decision Queue
Клиенты, которым нужно решение тренера

LOWER
Team Activity
Последние meaningful события

SECONDARY
Soft attention groups
Замеры, чек-ины, вес, ответы
```

### Основные секции

#### 1. Team Summary

Назначение:

- дать общее ощущение состояния команды;
- не превращаться в KPI-wall.

Пример:

```text
24 спортсмена · 18 по плану · 3 требуют действий · 2 ждут разбора
```

#### 2. Team Map

Назначение:

- показать всех клиентов как людей;
- сделать команду главным визуальным объектом;
- дать быстрый вход в профиль.

Статусы:

- по плану;
- нет следующей тренировки;
- ждет разбора;
- нужна корректировка;
- неактивен.

#### 3. Action Queue

Назначение:

- показать только тех, у кого тренировочный процесс заблокирован.

В очереди не должны жить все soft-issues.

Входят:

- нет следующей тренировки;
- тренировка ждет разбора;
- нет первой тренировки;
- цикл закончился;
- жалоба/травма требует корректировки плана.

#### 4. Team Activity

Назначение:

- показать живое движение команды;
- не требовать анализа.

Примеры:

- Артем завершил Push Day;
- Мария обновила вес;
- Егор получил новую тренировку;
- Ольга отправила чек-ин.

#### 5. Secondary Attention

Назначение:

- сгруппировать мягкие проблемы;
- не отвлекать от главного coaching flow.

Примеры:

- Нет замеров - 4 клиента;
- Нет чек-ина - 2 клиента;
- Не обновляли вес - 3 клиента.

### Primary action flow

```text
Тренер открывает главную
-> видит Team Map
-> замечает 3 клиента с блокировкой
-> нажимает "Обработать 3"
-> открывается первый Quick Assign / Review drawer
-> действие выполнено
-> следующий клиент
```

### Empty state: 0 clients

Если у тренера нет клиентов:

```text
Команда пока пустая
Добавьте первого клиента или откройте демо-команду
```

Действия:

- Добавить клиента;
- Пригласить по ссылке;
- Открыть демо-команду;
- Создать первый шаблон.

Важно: пустое состояние должно продавать не аналитику, а будущий coaching workflow.

### Success state: все клиенты в порядке

Если все клиенты идут по плану:

```text
Все клиенты идут по плану
```

При этом страница не должна становиться пустой.

Остаются:

- Team Map;
- последние события;
- ближайшие плановые действия;
- быстрый поиск клиента.

### Busy state: много срочных клиентов

Если много клиентов требуют действия:

- Team Map показывает напряжение, но не превращается в alarm wall;
- Action Queue ограничена 3-5 первыми клиентами;
- остальные группируются;
- тренер получает кнопку "Обработать по очереди".

### Почему это лучше традиционного dashboard

Традиционный dashboard показывает:

- метрики;
- графики;
- деньги;
- активность;
- отчеты.

Но тренеру утром нужен не отчет. Ему нужно понять:

```text
Кого открыть первым?
Что сделать?
Как перейти к следующему?
```

Главная Trainer OS выигрывает, если превращает внимание тренера в конкретное действие.

## 4. Аудит Client Profile

### Главный вопрос

Client Profile должен отвечать:

```text
Что происходит с этим спортсменом во времени?
```

Не:

```text
Вот запись клиента в базе данных.
```

### Общий вывод

Текущая версия уже ближе к premium athlete profile, чем к CRM, но часть структуры все еще выглядит как "карточка с данными":

- много facts;
- много tabs;
- часть важного контекста скрыта;
- Overview дублирует Header;
- Training, Progress и Timeline разнесены так, что тренер может терять историю принятия решений.

### Оценка секций

| Секция | Полезность | Частота | Cognitive load | Visual weight | Проблема |
|---|---|---:|---:|---:|---|
| Header | Высокая | Каждый визит | Средняя | Высокая | Много полей, но не всегда ясно текущее решение |
| Quick Actions | Высокая | Часто | Низкая | Средняя | Должны быть всегда доступны, но не превращать профиль в action screen |
| Overview | Средняя | Часто | Средняя | Средняя | Дублирует Header и не всегда добавляет новый смысл |
| Training | Очень высокая | Очень часто | Средняя | Недостаточная | Это ядро coaching profile, должно быть заметнее |
| Progress | Высокая | Периодически | Средняя | Средняя | Важно для анализа, но не каждый день |
| Timeline | Высокая | Часто | Средняя | Средняя | Должна быть историей решений, а не лентой событий |
| Notes | Высокая | Часто | Низкая | Недостаточная | Coach memory должен быть более доступным |

### Ненужные или спорные tabs

Текущая модель:

```text
Overview
Training
Progress
Timeline
```

Она понятна, но есть риск:

- Overview становится свалкой;
- Timeline дублирует Training и Progress;
- Notes/coach memory не имеет равного веса;
- важный текущий coaching state скрыт в одном из блоков.

### Рекомендуемая структура tabs

V1:

```text
Состояние
Тренировки
Прогресс
```

Постоянная правая или верхняя зона:

```text
Coach Memory / Notes
Open Issues
Next Decision
```

Почему:

- "Состояние" отвечает на вопрос "что с человеком сейчас";
- "Тренировки" отвечает на вопрос "как он тренируется";
- "Прогресс" отвечает на вопрос "куда он движется";
- notes и open issues не должны прятаться глубоко.

### Идеальный header

Header должен быть не CRM-шапкой, а athletic dossier.

Содержимое:

- avatar / photo;
- имя;
- цель;
- текущая фаза;
- текущий вес и target;
- readiness / recovery signal;
- last activity;
- next workout;
- current coaching status;
- primary next action.

Пример:

```text
Артем Смирнов
Набор массы · Неделя 4 из 8
74.2 кг -> цель 80 кг

Состояние:
Ждет разбора Push Day

Следующее решение:
Разобрать тренировку и назначить Pull Day
```

### Идеальные quick actions

Top actions:

- Назначить тренировку;
- Разобрать тренировку;
- Написать;
- Открыть конструктор.

Но важно:

- быстрые действия открываются в drawer;
- профиль остается местом понимания, а не местом быстрого conveyor-flow;
- после действия профиль обновляет current state.

### Идеальный training progression view

Главная проблема: previous loads и progression должны быть видны там, где тренер принимает решение.

Рекомендуемая структура:

```text
Training State
- Next workout
- Last workout
- Current split / phase
- Open training issue

Progression
- Key lifts
- Last / best / trend
- Recent changes

Workout History
- Compact chronological list
- Reviews attached to workouts
- Comments attached to sessions
```

Key lifts:

| Упражнение | Last | Best | Trend | Signal |
|---|---:|---:|---|---|
| Жим лежа | 80 x 6 | 82.5 x 5 | Up | можно +2.5 кг |
| Тяга | 120 x 5 | 125 x 3 | Flat | повторить |
| Присед | 100 x 6 | 105 x 5 | Down | проверить восстановление |

### Что скрыто, но нужно поднять

| Контекст | Почему важен |
|---|---|
| Текущий training blocker | Определяет next action |
| Previous loads | Нужны для назначения |
| Client comment from last workout | Помогает написать осмысленный review |
| Injury / limitations | Критично для корректировки |
| Coach notes | Создают ощущение персонального ведения |
| Communication history | Помогает помнить тональность и договоренности |

### Рекомендация

Client Profile должен стать:

```text
Athlete Dossier + Coaching State
```

Не:

```text
Client CRM record
```

## 5. Аудит drawers и модалок

### Правило принятия решения

```text
Если действие можно выполнить за 60 секунд - drawer.
Если нужно историческое понимание и анализ - full page.
Если есть быстрый и глубокий сценарии - hybrid.
```

### Рекомендации по workflow

| Workflow | Рекомендация | Почему |
|---|---|---|
| Quick Assign | Drawer | Это действие должно выполняться быстро и без потери контекста |
| Workout Review | Hybrid | Большинство разборов можно закрыть в drawer, но сложные случаи требуют full page |
| Message Client | Drawer | Быстрое сообщение не должно уводить из рабочего потока |
| Check-in Review | Hybrid | Обычный чек-ин можно закрыть в drawer, тревожный требует полного профиля |
| Measurements | Hybrid | Быстрый просмотр в drawer, глубокий анализ прогресса в profile/progress page |
| Template Selection | Drawer for selection, full page for editing | Выбрать шаблон быстро, редактировать шаблон глубоко |

### Quick Assign

Решение:

```text
Drawer
```

Почему:

- цель: назначить тренировку меньше чем за 60 секунд;
- тренер уже пришел из контекста клиента;
- нельзя заставлять его переходить в builder;
- вся нужная информация должна быть видна сразу.

Содержимое:

- client context;
- last workout;
- recommended next workout;
- template alternatives;
- previous loads;
- quick load strategy;
- assign / assign and next / open builder.

### Workout Review

Решение:

```text
Hybrid
```

Drawer для обычного review:

- summary;
- key signals;
- exceptions only;
- coach feedback presets;
- send review.

Full page для сложного review:

- все упражнения;
- видео/техника;
- история нагрузок;
- сравнение с планом;
- корректировка программы.

Почему:

80% тренировок должны разбираться быстро. Но премиальный тренер иногда нуждается в глубоком разборе.

### Message Client

Решение:

```text
Drawer
```

Почему:

- сообщение - это короткое действие;
- оно часто является завершением attention item;
- тренер не должен терять клиента, из которого пришел.

Важно:

- если реальная коммуникация в Telegram/WhatsApp, встроенные сообщения не должны становиться отдельным тяжелым inbox;
- лучше дать quick compose, шаблоны и копирование/отправку.

### Check-in Review

Решение:

```text
Hybrid
```

Drawer:

- самочувствие;
- сон;
- стресс;
- питание;
- комментарий;
- quick response.

Full page/profile:

- если есть тревожная динамика;
- если нужно сравнить несколько недель;
- если нужна корректировка плана.

### Measurements

Решение:

```text
Hybrid
```

Drawer:

- последний вес;
- изменение;
- фото/замеры;
- quick note.

Full page:

- долгосрочная динамика;
- фото-сравнения;
- тренды;
- decision making по фазе.

### Template Selection

Решение:

```text
Drawer for selection, full page for editing
```

Почему:

- выбор шаблона должен быть быстрым;
- создание и редактирование шаблона требует большего пространства.

Правильный flow:

```text
Quick Assign
-> выбрать шаблон в drawer
-> назначить

или

Quick Assign
-> Open Builder
-> глубокое редактирование
```

### Общая рекомендация

Drawers должны быть операционными инструментами, а не мини-страницами.

Хороший drawer:

- сохраняет контекст клиента;
- показывает только нужное для решения;
- имеет один главный action;
- закрывает задачу;
- предлагает "следующий клиент".

Плохой drawer:

- требует скроллить слишком много;
- дублирует full page;
- содержит аналитику;
- заставляет тренера думать, где он находится.

## 6. Дифференциация относительно Trainerize, TrueCoach, Everfit и My PT Hub

### Общий вывод

Большинство конкурентов продают похожий набор возможностей:

- workout builder;
- exercise library;
- templates;
- client management;
- messaging;
- habits/nutrition;
- calendar;
- payments;
- progress tracking;
- branded app;
- dashboards.

Это важные функции, но они уже стали commodity.

Trainer OS может отличаться не количеством разделов, а качеством ежедневного coaching workflow:

```text
Открыл систему
-> увидел, кто требует решения
-> назначил / разобрал / написал
-> закрыл задачу
-> перешел к следующему клиенту
```

### Top 5 differentiation opportunities

#### 1. Decision Queue вместо dashboard

Большинство платформ показывают данные. Trainer OS должен показывать решения.

Формула:

```text
Client + reason + recommended action
```

Пример:

```text
Артем
Нет следующей тренировки после Push Day
Рекомендация: назначить Pull Day
```

Почему это запоминается:

Тренер не хочет утром читать dashboard. Он хочет понять, кого обработать первым.

#### 2. Quick Assign как главный workflow

Если тренер может назначить следующую тренировку меньше чем за 60 секунд, это становится ежедневной привычкой.

Ключевые элементы:

- client context;
- last workout;
- recommended next template;
- previous loads;
- load strategy;
- assign and next client.

Почему это сильнее builder-first подхода:

Тренеру не всегда нужен конструктор. Часто ему нужно быстро принять повторяемое решение.

#### 3. Workout Review Inbox

Разбор тренировок должен ощущаться как обработка inbox:

```text
summary
signals
exceptions
feedback
send
next
```

Не как отчет и не как аналитический экран.

Почему это важно:

Премиальный тренер выигрывает качеством обратной связи. Если review быстрый, тренер реально делает его чаще.

#### 4. Athlete Profile как coaching dossier

Конкуренты часто делают client profile как CRM record.

Trainer OS может сделать его как:

```text
Athlete Dossier
```

То есть:

- состояние человека;
- история решений;
- текущий training blocker;
- previous loads;
- coach notes;
- ограничения;
- прогресс во времени.

Почему это дифференцирует:

Тренер чувствует, что система помогает помнить человека, а не хранит поля в базе.

#### 5. Team Map / Private Coaching Club

Team Map - самый визуально запоминающийся элемент.

Он показывает:

- всех клиентов как команду;
- кто в порядке;
- кто требует решения;
- где есть блокировки.

Но важно:

Team Map сам по себе не должен стать декоративной игрушкой. Его сила в том, что он ведет к действию.

### Самое перспективное направление

Самое сильное направление:

```text
Attention-driven Coaching OS
```

Не:

```text
еще одна фитнес-платформа
```

Позиционирование:

```text
Trainer OS helps premium coaches run their client roster like a private athlete team:
who needs a decision, what to do next, and how to move through the day fast.
```

На русском:

```text
Trainer OS помогает премиальному тренеру вести клиентов как частную спортивную команду:
видеть, кто требует решения, быстро назначать следующее действие и не терять контекст человека.
```

### Что заставит тренера сказать "я не хочу возвращаться в Trainerize"

Не просто красивый интерфейс.

А ощущение:

```text
Раньше я сам держал клиентов в голове.
Теперь система каждое утро показывает, кому нужно мое решение.
```

Ключевой retention moment:

```text
Тренер зашел утром
-> обработал 8 клиентов за 20 минут
-> назначил тренировки
-> отправил разборы
-> не открыл ни одной тяжелой таблицы
```

### Commodity features, которые не стоит приоритизировать

| Feature | Почему commodity |
|---|---|
| Exercise Library | Есть почти у всех, нужна, но не дифференцирует |
| Workout Builder | Базовая функция, важна, но не должна быть главным обещанием |
| Template Library | Нужна, но сама по себе не уникальна |
| Client List | Не дифференцирует, если это просто CRM roster |
| Messaging | Встроенный чат часто проигрывает Telegram/WhatsApp |
| Calendar | Полезен, но редко становится причиной перехода на продукт |
| Payments/Sales | Важны для бизнеса, но не ядро premium coaching workflow |
| Generic dashboards | У всех есть метрики, они не создают ежедневную привычку |
| Branded app | Продает, но не решает операционный день тренера |
| Nutrition/habits | Большая зона, но может размыть фокус V1 |

### Итоговая продуктовая ставка

V1 должен быть не самым широким продуктом.

Он должен быть самым ясным продуктом для ежедневного ведения 10-30 клиентов.

Фокус:

```text
Dashboard as Team Headquarters
Quick Assign
Workout Review Drawer
Athlete Profile
Templates
```

Отложить:

```text
Sales
Reports
Deep analytics
Automation
Calendar-first planning
Nutrition-heavy workflows
```

## Финальный вывод

Trainer OS V1 должен стать не CRM и не платформой "для всего".

Правильная формула:

```text
Private coaching team
-> visible state
-> clear decisions
-> fast drawers
-> athlete dossier
-> next client
```

Если это получится, главный экран не будет похож на dashboard. Он будет похож на рабочий штаб тренера, где каждый клиент - живой спортсмен, а каждое действие понятно за несколько секунд.
